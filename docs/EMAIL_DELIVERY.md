# B8 transactional email

Implementation is complete against isolated simulations; the owner explicitly chose not to supply real credentials on19 October2026. No message has been sent to an external inbox and production application/worker release gates remain closed. Live sending-domain, provider/inbox, abuse, data/retention and operator qualification remain separate launch requirements.

The existing Resend integration now uses durable encrypted delivery records, atomic provider-attempt claims and a fixed `bcs-email-{delivery UUID}` idempotency key. Provider I/O runs after the claim transaction commits. A crashed/uncertain claim can retry the same frozen recipient/from/subject/body within23 hours of its first attempt, inside Resend's24-hour deduplication window. Expired windows require external provider investigation, never automatic creation of another message. Five automatic attempts are bounded; independent current regional staff can authorize one further attempt at a time, up to50, with recent MFA, version checks, audit and the original key. Accepted/delivered/bounced/complained mail and old OTPs cannot be resent from staff recovery. A terminal failure remains a recorded failure rather than a false delivery success.

OTP requests accept an optional Idempotency-Key for backward compatibility; updated sign-in clients preserve it across uncertain requests. Exact retries preserve one challenge and encrypted code, changed locale/body conflicts, expired/superseded requests require a fresh code, and email/IP rate limits remain. Codes stay HMAC protected in the OTP table and authenticated encrypted in pending email content; sandbox codes are exposed only in the existing labelled development response. Actual provider acceptance returns SENT for compatibility, queued claims return PENDING, and only signed delivered receipts establish inbox delivery. OTP possession still does not establish adulthood or guardian authority.

Notifications are generic English/Hindi messages linking to authenticated screens; child names, academic records, payment amounts, bank details, staff notes, meeting links and invitation secrets are excluded. Event routing covers guardian/independent enquiries, reviewed shortlist publication and teacher responses, hiring and minimum-tuition updates, optional demos, support, optional supporter invitations and30-day placement follow-up. Teacher recipients come from the current published shortlist. Family consent/learner proof, current supporter grants, privacy pauses and disabled/changed accounts are rechecked before attempts. Internal support notes produce no owner email. Class-booking notifications remain within deferred class scope.

The worker atomically fans out outbox events to uniquely identified recipient deliveries, then dispatches them outside outbox transactions. Sandbox jobs explicitly finish SANDBOX and send no inbox message. Acceptance is distinct from delivery, delay, bounce and complaint. Email content is cleared after actual acceptance; encrypted sandbox OTP content lasts only until challenge expiry. Expired OTPs/content are purged; reviewed privacy erasure removes queued account and email-bound invitation content, including replay. Restricted attempt/receipt metadata remains under the approved retention review boundary.

Five documented operations provide current-account notification pages, fresh-MFA regional staff queues, independently paginated attempts/receipts, versioned reviewed retries and raw signed Resend receipts. Metadata projections exclude addresses, code/content, recipient hashes, request hashes and secrets. Only administrators can inspect anonymous OTP metadata; regional operators cannot. Staff may inspect the provider reference for external investigation.

For future provider qualification inject EMAIL_DELIVERY_MODE=resend, RESEND_API_KEY, EMAIL_FROM on a verified domain, PUBLIC_APP_URL and a dedicated32-byte base64 EMAIL_CONTENT_KEY; configure EMAIL_WEBHOOK_SECRET securely from Resend/Svix. Development alone may derive an isolated content key from the existing OTP key. Never commit keys or paste them into chat. Subscribe the provider endpoint `/api/v1/notifications/webhooks/resend` to email.sent, email.delivered, email.delivery_delayed, email.bounced and email.complained. It verifies Svix HMAC-SHA256 against the exact raw bytes with a five-minute signature window, deduplicates event identity/body digest, tolerates early/out-of-order supported receipts and stores no raw provider payload. Generic origin exemptions apply only to the exact signed webhook path; other writes retain Origin/CSRF checks.

Live qualification must validate the current provider deduplication contract, actual sending identity/domain, recipient delivery, signing-secret custody/rotation, failure/complaint handling and external provider retention/deletion. Those operations were intentionally not performed without credentials. No deployment is authorized by this feature.

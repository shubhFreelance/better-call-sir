## Open QA finding: guardian-only subject preferences

A separate real-API probe on the activated guardian-only child returns403 from `POST /children/:id/learning-spaces` but201 from `POST /onboarding/student/confirmations` with the same Maths/English space, and confirms that the latter writes the canonical child space. The probe completes the full linked journey successfully afterwards; this observation is not counted as another unique acceptance case.

Existing student-onboarding design explicitly permits personal preferences without transferring hiring authority, and the normal suites intentionally cover that behavior. However, the two API routes enforce different permission rules, and “Guardian manages everything” can imply a stricter read-only child account. Teacher-choice/consent/financial authority remains protected in the tested APIs. This is an open product/authorization-consistency finding, not evidence that the child can hire or consent independently.

Next: align the intended guardian-only preference policy, API entry points and UI wording/actions. If guardian-only means read-only preferences, both onboarding writes and the Create spaces UI need corresponding restrictions and regression checks; otherwise the direct space API and copy must consistently distinguish preferences from tuition authority. This audit preserves existing behavior rather than silently changing the approved optional-preferences design. Dependency security remediation follows this flow clarification.

## Current rules and useful next refinement

- 18+ independent signup and guardian-managed/shared access for younger learners are distinct paths. School class or self-confidence does not turn a minor into an independent adult account.
- Guardian verification is per relationship/per child. A verified parent can manage multiple children, but one child's approval does not substitute for another child's review. Learning permission and student account access are separate from that approval.
- If the guardian supplied an existing student's email and the student acknowledged it, saving the approved learner profile links that account automatically. If the guardian used a staff-observed acknowledgment without a student email, share an invitation after setup; the student verifies their own email. Do not create a second learner to give the existing child sign-in access.
- After activation, students use ordinary email sign-in. A new invitation is not required for every login.
- Useful future refinement: refresh pending approval/acknowledgment status automatically while the screen is idle, preserving unsaved inputs and requiring fresh confirmation for changed decisions. This QA used the existing explicit refresh controls; continuous cross-browser status updates are not newly implemented here.

## Reproduce

With dependencies/generated Prisma client installed and ports4000/3002 free:

```sh
docker compose -f infra/compose/development.yaml up -d --wait
npm run scanner:test:setup
npm run build -w @bcs/web
npm run test:family-qa
```

Use the loopback database settings in `.env` or `.env.example`. The suite builds the API/worker, uses the production frontend on3002 and performs no API route mocking. It applies checked-in migration SQL only to its generated disposable database.

```sh
BCS_TEST_SQL_MIGRATIONS=1 npm run test:integration
npm run test:production-browser -- guardian-verification guardian-priorities guardian-learners guardian-guidance independent-student student-connection returning-account onboarding-recovery
```

On PowerShell, set `$env:BCS_TEST_SQL_MIGRATIONS = "1"` before the integration command. The normal migration runner remains the default when that explicit SQL acceptance flag is absent.
